Ticketing PKI Certificate Policy

Abstract

This document describes the certificate policy for a Public Key Infrastructure (PKI) used to support the issuance and validation of barcodes for transport ticketing. Each organisation that issues such tickets will obtain a certificate under this TPKI for providing a digital signature over their tickets. These certificates will allow other transport undertakings to verify the authenticity of the ticket barcodes and the issuer's authorisation to issue such tickets.¶

This note is to be removed before publishing as an RFC.¶

The OIDs assigned in this document under 1.3.6.1.4.1.56292.1.3 are not final, and are merely assigned for experimentation purposes.¶

1. Introduction

This document describes the certificate policy for a Public Key Infrastructure (PKI) used to support the issuance and validation of barcodes for transport ticketing - a Ticketing PKI (TPKI). This PKI is designed exclusively for use in support of validation of claims relating to transport ticketing via barcoded tickets. Use of the certificates, Certificate Revocation Lists (CRLs), or any other artifact managed under this PKI for any other purpose is a violation of this CP, and relying parties (RPs) MUST reject certificates presented for such uses.¶

This document is based on the template specified in[RFC3647], a product of the Internet Engineering Task Force (IETF) stream. Its section numbering has been maintained to allow direct comparison of Certificate Policies and Certification Practice Statements. Certification Practice Statements issued under this PKI MUST retain the same section numbering.¶

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in [BCP14] when, and only when, they appear in all capitals, as shown here.¶

1.1. Overview

This document defines a set of technologies, rules, and requirements necessary - but not sufficient - for the operation of a PKI for Ticketing (TPKI). Certificates issued in this PKI are trusted by virtue of their corresponding root CA being installed on the ticket control device concerned.¶

It is envisaged that there may be several roots in a global TPKI ecosystem. Each of these root CAs will exist to serve a different market. The primary of these will be the UIC's root.¶

This CP sets a common set of rules that all root CAs must follow, regardless of their specifics of operation, to ensure adequate interoperability between root CAs. Each root CA, and each subordinate CA thereof, MUST create and publish a CPS, in compliance with this CP.¶

These requirements are applicable to all participants in a TPKI.¶

In the event of a disagreement between this document and other agreements in the TPKI, this document has precedence.¶

1.3. PKI participants

1.3.1. Certification authorities

The CA is this PKI is responsible for the issuance of certificates in accordance with this CP and its CPS. The primary CA is the root CA. Other participants may be CA insofar as they issue STAR certificates.¶

1.3.2. Registration authorities

The registration authority is responsible for verifying that applications for new certificate issuance are legitimate and in accordance with this CP and its CPS. The RA checks the subscriber's authority to hold such a certificate, and that this is a genuine request of the subscriber.¶

It is envisaged that the CA and the RA roles are primarily performed by the same entity, but this CP does not preclude the separation of these functions.¶

1.3.3. Subscribers

Subscribers are those entities that receive a certificate under this TPKI for signing ticket barcodes. These could be a transport undertaking directly issuing their own tickets, or an organisation authorised to distribute tickets but not operating transport services themselves.¶

1.3.4. Relying parties

Relying parties are those entities that use certificates from this TPKI to verify the authenticity of tickets barcodes. These are primarily transport undertakings verifying tickets on-board their services.¶

A relying party may also be a subscriber if they issue tickets as well as verify them.¶

1.3.5. Other participants

All CAs in the TPKI are responsible for publishing certain artefacts. These duties MAY be performed by the CA directly, or MAY be outsourced.¶

1.4. Certificate usage

1.4.1. Appropriate certificate uses

Certificates issued under this CP MAY be used for the purposes of verifying ticket barcodes.¶

1.4.2. Prohibited certificate uses

Certificates issued under this CP MUST NOT be accepted for any use outside that of verifying tickets for transport purposes.¶

2. Publication and Repository Responsibilities

2.1. Repositories

Certificates and CRLs MUST be made available for downloading by all relying parties. Each CA MUST maintain an online, publicly accessible, repository of all certificates and CRLs issued.¶

Certificates an CRLs MUST be provided over HTTP with TLS[RFC9110]. The certificate repository MUST be a DER encoded "certs-only" CMS message as specified in[RFC2797].¶

A CA MAY publish certificates and CRLs via other means, in addition.¶

2.2. Publication of certification information

Each CA MUST publish the certificates, except STAR certificates, that it issues.¶

Each CA MUST publish the CRLs that it issues.¶

Each CA MUST create and publish a CPS that meets the requirements set forth in this CP. Publication means that the CPS is openly available to the public. It is RECOMMENDED that this be via publication on a website.¶

An organisation MAY choose to outsource the publication of data.¶

2.3. Time or frequency of publication

The CPS for each CA MUST specify the following information:¶

  1. The period of time within which a certificate will be published after the CA issues the certificate.¶
  2. The period of time within which a CA will publish a CRL with an entry for a revoked certificate after it revokes that certificate.¶

The CA MUST maintain version control on its CPS, allow retrieval of older versions of its CPS, and indicate when and how its CPS was updated via changelog.¶

2.4. Access controls on repositories

Participants MUST make their repositories publicly available in a read-only manner.¶

3. Identification and Authentication

3.1. Naming

3.1.1. Types of names

3.1.1.1. Standard certificates

Subjects of certificates are identified via an X.500 Distinguished Name. A name MUST contain:¶

  • ISO 3166 [ISO3166-1] Country Code (2.5.4.6) - country in which the subject is incorporated.¶
  • Organisation name (2.5.4.10) - full legal name of the subject.¶
  • Company code (1.3.6.1.4.1.56292.1.3.2.1, seeAppendix A.1.1) - the UIC RICS of the subject or, if no RICS is available, an otherwise specified company code as per the CA's CPS.¶

A name MAY also contain:¶

  • State or province name (2.5.4.8) - first level administrative subdivision in which the subject is incorporated, per ISO 3166 part 2[ISO3166-2].¶

In the case of an end-entity certificate (i.e. one used to sign tickets) the following attributes MUST be present:¶

  • Key ID (1.3.6.1.4.1.56292.1.3.2.2, seeAppendix A.1.2) - a unique identifier for a subject's key pair, to allow for correlating public keys and signatures in tickets.¶

In the case of non end-entity certificates, the following attributes MUST be present:¶

  • Common Name (2.5.4.3) - a textual description of the purpose of this certificate, e.g. "UIC Root CA" or "UIC Intermediate CA 1"¶

A CA may, in its CPS, define the inclusion of other attributes.¶

3.1.1.2. STAR Certificates

A STAR certificate, per specification, contains a company code, and a serial number. No other forms of naming ar permissible.¶

3.1.2. Need for names to be meaningful

Names in this TPKI MUST be meaningful. It SHALL be possible to map from a name within a certificate to a legal entity, and thus who is responsible for a certificate and its corresponding private key.¶

3.1.3. Anonymity or pseudonymity of subscribers

Subscribers to this PKI SHALL NOT be anonymous.¶

3.1.4. Rules for interpreting various name forms

3.1.4.1. Standard certificates

The primary identifier of a certificate is the combination of company code and key ID. That alone MUST be sufficient to identify a certificate, and therefore public key, for verifying a ticket barcode.¶

3.1.4.2. STAR Certificates

STAR Certificates are identified by their inclusion in a ticket barcode. Their serial number exists only to effectuate the checking of the revocation status of a STAR certificate.¶

3.1.5. Uniqueness of names

Names within this PKI MUST be unique. No certificate is permitted to be issued with an identical subject name, unless it is issued to the same legal entity for the same subject public key information as an extant certificate.¶

4. Certificate Life-Cycle Operational Requirements

4.1. Certificate Application

4.1.1. Who can submit a certificate application

Any entity wishing to issue ticketing barcodes SHOULD obtain a certificate from a CA suitable for the environment in which their barcodes will be verified, e.g. the UIC CA for international railway ticketing.¶

The application procedure MUST be described in the CPS for each CA.¶

4.1.2. Enrollment process and responsibilities

The applicant MUST generate a key pair themselves and communicate such public key to the RA along with their application particulars. No party is permitted to generate the key pair on behalf of the applicant. The RA verifies the application, and communicates the request to the CA for issuance, via a secured channel.¶

The exact details of the application particulars MUST be described in the CPS for each CA.¶

4.2. Certificate application processing

CAs SHOULD make use of extant standards for processing certificate requests. Each CA MUST define in its CPS, the certificate request and response standards that it employs.¶

4.2.1. Performing identification and authentication functions

It is the responsibility of the RA to verify the providence of applications, and that the application is allowable per this TPKI and its CPS. The legal identity of the applicant organisation MUST be established, as certificates in this TPKI are bound to legal entities.¶

4.2.2. Approval or rejection of certificate applications

The details of how certificate applications are approved MUST be described in the CA's CPS¶

4.2.3. Time to process certificate applications

No stipulation.¶

4.3. Certificate issuance

4.3.1. CA actions during certificate issuance

4.6. Certificate renewal

4.6.1. Circumstance for certificate renewal

4.6.1.1. Standard Certificates

Certificates in this TPKI MUST NOT be renewed. Once a key ID (see Section 3.1.1.1) is attached to a public key, that public key is considered 'spent', and a certificate with that public key MUST NOT be further renewed beyond its original lifetime. This stipulation does not apply to STAR certificates, as they do not include a key ID.¶

4.6.1.2. STAR Certificates

A STAR certificate may be renewed up to the cryptographic lifetime of its public key.¶

A renewed STAR certificate MUST be identical to the old certificate, except for a new serial number, and different validity dates. The validity dates SHOULD overlap.¶

4.6.2. Who may request renewal

4.6.2.1. Standard Certificates

Not applicable.¶

4.6.2.2. STAR Certificates

Only the certificate holder or the issuing CA may initiate renewal. The certificate holder MAYrequest an early renewal, if it, as an example, expects to be unavailable to support the renewal process during the normal expiration period. An issuing CA MAY initiate the renewal process based on the certificate expiration date.¶

4.6.3. Processing certificate renewal requests

4.6.3.1. Standard Certificates

Not applicable.¶

4.6.3.2. STAR Certificates

The CA MUST verify that the certificate has not been revoked before renewing it. It MUST issue the renewed certificate to the same subject public key.¶

7. Certificate, CRL, and OCSP Profiles

7.1. Certificate profile

7.1.1. Version number(s)

For standard certificates they MUST be version 3 certificates as per [RFC5280]. For STAR Certificates they MUST follow the format defined in Appendix B.¶

7.1.2. Certificate extensions

7.1.2.1. Root CA

Root CA certificates in this PKI MUST include the following extensions:¶

  • basicConstraints; MUST be critical; MUST have cA set to true, and MUST NOT not have a path length constraint.¶
  • keyUsage; MUST be critical; MUST assert only keyCertSign and cRLSign.¶
  • extKeyUsage; MUST be critical; MUST assert only the Trust Anchor EKU, see Appendix A.2.1.¶
  • subjectKeyIdentifier; MUST NOT be critical.¶
  • authorityKeyIdentifier; MUST NOT be critical; MUST include only keyIdentifier with a value identical to subjectKeyIdentifier.¶
  • certificatePolicies; see Section 7.1.6.¶

Root CA certificates MAY include other extensions, per the CA's CPS.¶

Certificates which do not assert the Trust Anchor EKU MUST NOT be accepted by relying parties as a root of trust.¶

7.1.3. Algorithm object identifiers

For the following cryptographic algorithms, the following OIDs MUST be used:¶

  • NIST ECC P-256: 1.2.840.10045.3.1.7¶
  • NIST ECC P-384: 1.3.132.0.34¶
  • NIST ECC P-521: 1.3.132.0.35¶
  • TODO: more¶

Elliptic curve subject public keys MUST used a named curve OID, and MUST NOT use explicit curve parameters.¶

A CA MAY, in its CPS, define the OIDs it uses for other cryptographic algorithms.¶

7.1.4. Name forms

Section 3.1.1.1 defines the required and optional name attributes in this PKI.¶

For each certificate the value of the issuer field MUST be byte-for-byte identical to the value of the subject field of the issuing CA certificate.¶

When encoding a name, CAs MUST encode them as such:¶

  • A name MUST be an RDNSequence.¶
  • Each RelativeDistinguishedName MUST contain exactly one AttributeTypeAndValue.¶

  • RelativeDistinguishedNames MUST be placed in the RDNSequence in the following order:¶

    1. ISO 3166 Country Code¶
    2. State or province name¶
    3. Organisation name¶
    4. Company code¶
    5. Common name¶
    6. Any CA specific attributes¶
    7. Key ID¶
  • Each Name MUST NOT contain more than one instance of a given AttributeTypeAndValue.¶

7.1.5. Name constraints

Name constraints MUST NOT be used in this PKI.¶

7.1.6. Certificate policy object identifier

For standard certificates, the certificate policy extension MUST be included, asserting this document's OID, as defined inSection 1.2. This extension MUST be marked critical.¶

7.1.7. Usage of Policy Constraints extension

This extension MUST NOT be present.¶

7.1.8. Policy qualifiers syntax and semantics

The certificate policy extension MUST include the CA's CPS in a CPSuri qualifier.¶

A CA MAY include a textual notice in its policy qualifiers. If it does so it MUST use the explicitText form. A relying party encountering such a notice MUST display it during ticket control.¶

7.1.9. Processing semantics for the critical Certificate Policies extension

Relying parties MUST reject certificates asserting a CP they do not deem acceptable.¶

7.2. CRL Profile

7.2.1. Version number(s)

CAs MUST issue version 2 CRLs as per [RFC5280]. CRLs MUST NOT include Indirect or Delta CRLs. The scope of each CRL MUST be all certificates issued by a CA.¶

The contents of the CRL is a list of all non-expired certificates that have been revoked by the CA. Where two or more CRLs are issued by the same CA, the CRL with the highest value of the "CRL Number" field supersedes all other CRLs issued by this CA.¶

7.2.2. CRL and CRL entry extensions

A CRL MUST include the CRL Number and the Authority Key Identifier extensions. A CRL MUST NOT include any other extension.¶

A CRL entry MUST include a Reason extension.¶

A CRL entry MAY include a Revocation Notice extension (see Appendix A.3.1). If present, relying parties MUST display this during ticket inspection.¶

A CRL entry MUST NOT include any other extensions.¶

7.3. OCSP Profile

7.3.1. Version number(s)

A CA MUST provide a version 1 OCSP service as per [RFC6960].¶

CAs MUST generate a separate OCSP responder certificate, they MUST NOT use the CA certificate to sign OCSP responses.¶

7.3.2. OCSP extensions

CAs MUST support the OCSP Nonce extension.¶

CAs MAY support other responseExtensions.¶

The singleExtensions of an OCSP response MUST NOT contain the reasonCode CRL entry extension.¶

The singleExtensions of an OCSP response MAY contain the Revocation Notice extension. It MUST be present if also present in the CRL, and vice versa. Relying parties MUST process it the same as if it was in the CRL.¶

The singleExtensions of an OCSP response MUST NOT contain any other extension.¶

Appendix A. ASN.1 Definitions

This section details the additional ASN.1 elements defined in addition to those of [RFC5280] that are required for the operation of a TPKI.¶

OIDs defined for these extensions are under the following arc:¶

id-as207960-uic OBJECT IDENTIFIER ::= { 1 3 6 1 4 1 56292 1 3 }
¶

A.1. Name Attributes

This document defines two new name attributes for identifying companies and their signing keys in their certificates.¶

Name Attributes are defined under the following arc:¶

id-at OBJECT IDENTIFIER ::= { id-as207960-uic 2 }
¶

A.1.1. Company Code Name Attribute

This attribute is defined by the following OID and ASN.1:¶

id-at-companyCode OBJECT IDENTIFIER ::= { id-at 1 }
X520CompanyCode ::= CompanyCode

CompanyCode ::= CHOICE {
  codeNum INTEGER (1..32000),
  codeIA5 IA5String
}
¶

The codeNum variant MUST be used in case the organisation has a RICS code, or is otherwise identified by a numeric ID. The numbers 0 through 9999 MUST only be used to specify RICS codes, other coding schemes MUST be placed above 9999.¶

The codeIA5 variant MAY be used in case the organisation has an ERA company code, but no RICS code, or is otherwise only identified by an alphanumeric code.¶

A.1.2. Key ID Attribute

This attribute is used in the ticket barcode to identify the end-entity certificate used to verify the ticket. The combination of the company code and key ID uniquely identifies the key pair used to sign the ticket.¶

The attribute is defined by the following OID and ASN.1:¶

it-at-keyId OBJECT IDENTIFIER ::= { id-at 2 }
X520KeyId ::= Choice {
  number INTEGER (0..99999), -- For DOSIPAS envelopes,
  ia5 IA5String (SIZE (5)) -- For #UT envelopes
}
¶

In the case of a purely numeric key ID, the number variant SHALL be used, otherwise the ia5 variant SHALL be used.¶

A.2. Extended Key Usages

Extended Key Usages are defined under the following arc:¶

id-eku OBJECT IDENTIFIER ::= { id-as207960-uic 1 }
¶

A.2.1. Trust Anchor EKU

This EKU is defined by the following OID:¶

id-eku-trustAnchor OBJECT IDENTIFIER ::= { id-eku 1 }
¶

This EKU marks that a certificate is intended to be used as a trust anchor.¶

A.3. Certificate Extensions

Certificate Extensions are defined under the following arc:¶

id-ext OBJECT IDENTIFIER ::= { id-as207960-uic 3 }
¶

A.3.1. Revocation Notice Extension

This extension defines a notice to be displayed to inspection staff upon encountering a revoked certificate.¶
